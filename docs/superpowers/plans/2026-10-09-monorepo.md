# 모노레포 전환 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 동작을 바꾸지 않고 저장소를 `services/board`, `services/web`, `build-logic`, `deploy`로 나누고, 서비스별 CI와 공통 빌드 규칙을 갖춘다.

**Architecture:** 루트에 Gradle 빌드 하나를 두고 board를 `:services:board`로 등록한다. 품질 규칙은 `build-logic`(included build)의 컨벤션 플러그인 두 개로 옮긴다. 먼저 규칙을 플러그인으로 옮겨 동등성을 증명한 뒤(작업 1), 위치를 옮긴다(작업 2~4). CI와 의존성 갱신은 서비스별 포함 목록으로 바꾼다(작업 5).

**Tech Stack:** Gradle 9 (Kotlin DSL, precompiled script plugins), Spring Boot 4.1, pnpm 11, Docker Compose, Keycloak 26, GitHub Actions, Dependabot

**Spec:** [ADR-0014](../../project/adr/0014-monorepo-with-gradle-convention-plugins.md), [PRJ-SRS 1.5.0](../../project/srs.md) (COM-NFR-006·031~035, COM-CON-004·006), [PRJ-SDS 1.6.0](../../project/sds.md) §9·§10, [PRJ-QC 1.0.0](../../project/qa-checklist.md)

## Global Constraints

- COM-NFR-031: 코드 포맷, 정적 분석, null 안정성, 테스트, 커버리지 기준 중 하나라도 위반하면 빌드가 실패한다.
- COM-NFR-034: 모든 Java 서비스는 공통 빌드 규칙으로 같은 품질 기준을 적용받는다. 서비스의 빌드 스크립트에 품질 규칙을 복사하지 않는다.
- COM-NFR-033: 변경된 서비스의 검증만 자동 실행한다. Java 공통 빌드 파일이 바뀌면 모든 Java 서비스를 검증한다.
- COM-NFR-035: Gradle, npm, GitHub Actions, 컨테이너 이미지를 모두 자동 갱신한다.
- COM-NFR-006: 개발 환경 포트는 기본적으로 `127.0.0.1`에만 열고, 접속 정보와 바인딩 주소는 환경 변수로 바꿀 수 있다.
- COM-CON-004: `docker compose -f deploy/compose.yaml up -d` 한 번으로 외부 시스템이 준비되고, `.env`가 없어도 동작한다.
- COM-CON-006: 시험 사용자는 realm 구조와 분리하고 개발 환경에서만 가져온다.
- COM-CON-001: Java 25, Spring Boot 4.1 계열.
- **동작 불변:** Java 패키지(`com.board.bbs`), `spring.application.name`(`bbs`), API, 테스트 내용은 바꾸지 않는다. 테스트 수는 전환 전후 모두 140개다.
- **이력 보존:** 파일 이동은 `git mv`로 한다.
- **빈 모듈 금지:** `services/auth`, `libs/`, `deploy/traefik/`을 만들지 않는다.
- **문서 동반:** 각 작업은 자기가 바꾸는 경로를 언급하는 문서(README, `CLAUDE.md`, 코딩 표준, 기능 SDS)를 같은 커밋에서 고친다. 기능 문서를 고치면 버전을 올리고 `related`를 맞춘다 (`docs/README.md` §6).
- 커밋 메시지는 `type(scope): subject`, 본문 끝에 `Co-Authored-By` 줄.

## Review Focus

1. **Gradle 클래스로더 충돌:** 루트가 `alias(libs.plugins.spotless)`로 Spotless를 적용하고 `build-logic`도 Spotless를 의존성으로 가지면, 서브프로젝트에서 "plugin already on the classpath" 오류나 확장 타입 불일치가 날 수 있다. 작업 2의 검증 단계에서 루트와 board의 `spotlessCheck`가 모두 실행되는지 확인한다.
2. **작업 디렉터리 의존:** board의 실행 위치가 루트에서 `services/board`로 바뀐다. 상대 경로로 파일을 읽는 코드(`ComposeImages`, docker compose 연동)가 IDE·Gradle·CI 어디서 실행해도 같은 파일을 찾아야 한다. 작업 2와 4에서 `ComposeImagesTest#저장소의_compose_파일에서_읽는다`와 `bootRun`으로 확인한다.
3. **품질 규칙의 조용한 누락:** 규칙이 플러그인으로 옮겨지면서 빠져도 기존 테스트는 모두 통과한다. 작업 1에서 위반 코드를 넣어 빌드가 실패하는지(TC-COM-001, 002)와 실행되는 검증 작업 목록이 전환 전과 같은지 비교한다.
4. **Keycloak 사용자 파일 가져오기:** 사용자 파일을 분리한 뒤 Keycloak이 이 파일을 가져오지 않아도 compose는 정상으로 뜬다. 작업 4에서 컨테이너를 새로 만들고 관리 API 또는 E2E 로그인으로 `tester`가 있는지 확인한다.
5. **CI 경로 필터 누락:** 포함 목록에서 공통 파일을 빠뜨리면 검증이 조용히 생략된다. 작업 5에서 워크플로 문법을 검사하고, PR에서 두 워크플로가 실제로 실행되는지 확인한다(TC-COM-005, 006).

클래스로더 충돌이 나면: 루트의 Spotless를 `build-logic`의 세 번째 플러그인 `bbs.repository-conventions`(Gradle 스크립트 포맷과 `installGitHooks`)로 옮기고 루트는 그 플러그인만 적용한다. 이 결정을 진행 기록에 Ruling으로 남기고 SDS §10.1 표에 행을 추가한다.
