# ADR-0015. 화면은 Angular로 유지한다

- 상태: Accepted
- 일자: 2026-10-09
- 관련: COM-NFR-032, COM-CON-003, [ADR-0008](0008-oidc-bff-and-redis-session.md), [ADR-0014](0014-monorepo-with-gradle-convention-plugins.md), [코딩 표준 §2.2·§5](../coding-standards.md#5-프론트엔드-규칙)

## 맥락

- 화면은 Angular SPA로 만들어져 있다. 게시글·댓글 화면, 인증 연동(BFF 세션 쿠키), OpenAPI 생성 타입, Vitest·MSW·Playwright 테스트, 코딩 표준(CS-F01~F08)이 모두 Angular를 기준으로 정리되어 있다. 다만 Angular를 고른 근거는 SDS의 기술 스택 표에 한 줄로만 남아 있었다.
- 모노레포 전환([ADR-0014](0014-monorepo-with-gradle-convention-plugins.md))을 앞두고, 화면 기술을 그대로 옮길지 이 시점에 바꿀지 판단해야 했다.
- 이 프로젝트의 화면 개발은 AI 코딩 도구에 크게 의존한다. 개발자가 화면 기술을 깊이 학습할 계획은 당분간 없으므로, 생성된 코드의 잘못을 사람의 리뷰보다 **도구(타입, 린트, 테스트)가 먼저 잡아야** 한다.
- 따라서 선택 기준은 (1) AI가 일관된 코드를 만들기 쉬운가, (2) 장기간 관리되고 업그레이드 경로가 예측 가능한가, (3) 사용자 만족도, (4) 기존 구조(JSON API, BFF, 동일 오리진)와 맞는가였다.
- 참고한 자료(2026-10-09 기준): Stack Overflow Developer Survey 2026의 웹 프레임워크 사용률은 React 41.5%, Next.js 20.6%, Vue.js 17.2%, Angular 16.0%, Svelte 7.8%였다. State of JavaScript 2025에서는 프레임워크 사용 순위가 거의 변하지 않았고, Next.js는 사용률이 늘었지만 만족도가 떨어졌다.

## 결정

- 화면은 계속 **Angular**로 만든다. 프레임워크가 제공하는 라우터, 폼, HTTP 클라이언트, DI를 쓰고, 같은 역할의 외부 라이브러리를 추가하지 않는다.
- AI가 예전 방식(NgModule, 생성자 주입, Zone 기반 변경 감지)의 코드를 만들 수 있으므로, 현재 방식(standalone 컴포넌트, `inject()`, signal, `OnPush`, `httpResource`)을 코딩 표준과 린트로 강제한다. 린트로 강제할 수 없는 규칙은 리뷰에서 규칙 번호로 지적한다.
- 메이저 버전은 Angular의 출시 주기를 따라 `ng update`로 올린다. 지원이 끝난 버전에 머물지 않는다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| HTMX (+ jQuery) | 화면 코드는 가장 적지만, 서버가 HTML 조각을 응답해야 한다. JSON API, OpenAPI 타입 계약(COM-NFR-032), 서비스 분리 계획을 다시 설계해야 한다. HTMX와 함께라면 jQuery는 거의 필요 없다 |
| SvelteKit | 만족도가 높지만, Svelte 5에서 문법이 크게 바뀌어(runes) AI가 이전 문법을 섞어 생성하기 쉽다. 생성된 코드를 사람이 검토하기 어려운 조건에서 위험이 크다 |
| Next.js | 사용률은 높지만 만족도가 하락 추세다. 서버 기능 대부분이 이미 BFF(ADR-0008)와 겹치고, 배포 방식이 특정 플랫폼에 기울어 있다 |
| TanStack Start (React) | 만족도와 관심이 높지만 역사가 짧아 API가 바뀔 여지가 있고, AI가 참고할 자료가 적다. React가 필요해지면 가장 먼저 검토할 후보다 |

## 결과

- 좋은 점: 전환 비용이 없다. 프레임워크가 구조를 정해 두어서 AI가 만든 코드의 편차가 작고, 타입·린트·테스트가 잘못을 잡는다. Google이 관리하고 출시·지원 주기가 공개되어 있어 장기 유지보수를 예측할 수 있다. 백엔드(Spring)와 비슷한 DI·서비스 구조라 이해하기 쉽다.
- 나쁜 점: 업계 사용률이 React보다 훨씬 낮아 참고 자료, 예제, 채용 시장이 작다. AI가 예전 방식의 Angular 코드를 만드는 경우가 있어 린트와 리뷰 규칙을 계속 관리해야 한다. React 생태계의 UI 라이브러리를 그대로 쓸 수 없다.
- 재검토 조건: Angular의 장기 지원 정책이나 관리 주체가 바뀔 때. AI 도구가 Angular 코드를 일관되게 만들지 못해 같은 리뷰 지적이 반복될 때. 화면에 SSR이나 React 생태계에만 있는 기능이 필요해질 때.
