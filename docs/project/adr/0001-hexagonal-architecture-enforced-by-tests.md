# ADR-0001. 헥사고날 아키텍처를 쓰고 테스트로 강제한다

- 상태: Accepted
- 일자: 2026-09-18
- 관련: COM-NFR-030, [프로젝트 SDS §4](../sds.md#4-구성과-의존-관점)

## 맥락

학습 목표는 "설계 의도가 코드와 빌드로 강제되는 구조"다. 계층형 구조(controller → service → repository)는 익숙하지만, 서비스가 JPA 엔티티를 그대로 다루면서 도메인 규칙이 서비스, 엔티티, 컨트롤러에 흩어지기 쉽다. 또한 1인 개발이므로 구조 위반을 지적해 줄 리뷰어가 없다.

## 결정

- 기능별 패키지 안을 `domain` / `application`(`port.in`, `port.out`, `service`) / `adapter`(`in`, `out`)로 나눈다.
- 의존은 `adapter → application → domain` 한 방향으로만 흐른다.
- 이 규칙을 ArchUnit 테스트(`HexagonalArchitectureTest`)로 작성해서 `./gradlew check`에 포함한다. 규칙을 어기면 빌드가 실패한다.
- 아키텍처 테스트는 첫 수직 슬라이스(게시글 작성·조회) 직후에 추가한다. 마지막에 추가하면 그 전에 쌓인 위반을 한꺼번에 고쳐야 한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 계층형 구조 + 코드 리뷰로 규칙 유지 | 리뷰어가 없다. 문서로 적은 규칙은 시간이 지나면 지켜지지 않는다 |
| Gradle 멀티 모듈로 계층 분리 | 컴파일 수준에서 강제되지만, 기능 수가 적은 프로젝트에 빌드 구성이 과도하다 |
| Spring Modulith | 기능 경계 검증에는 적합하지만 계층 규칙은 따로 작성해야 한다. 학습 목적상 규칙을 직접 작성하는 편이 낫다고 판단했다 |

## 결과

- 좋은 점: 도메인 테스트가 스프링 없이 밀리초 단위로 돈다. 규칙 위반이 즉시 빌드 실패로 드러난다.
- 나쁜 점: 포트 인터페이스와 매퍼 등 파일 수가 늘어난다. 단순한 CRUD에도 여러 파일을 만들어야 한다.
- 후속: 계층 규칙만으로는 기능 사이의 순환을 막지 못해서 [ADR-0009](0009-feature-boundaries-via-events.md)를 추가했다.
