# ADR-0008. 인증은 OIDC BFF 방식, 세션은 Redis에 둔다

- 상태: Accepted
- 일자: 2026-09-18
- 관련: COM-NFR-001, COM-NFR-002, COM-NFR-003, COM-NFR-020, MEM-FR-001

## 맥락

인증을 직접 구현하지 않고 외부 IdP(Keycloak)에 맡기기로 했다. SPA가 토큰을 직접 보관하는 방식과 서버가 토큰을 보관하고 브라우저에는 세션 쿠키만 주는 방식(BFF, Backend for Frontend) 중 하나를 골라야 한다.

## 결정

- Spring Security `oauth2Login`으로 Authorization Code 흐름을 처리하고, 토큰은 서버에만 둔다.
- 세션은 Spring Session으로 Redis에 저장해서 애플리케이션 인스턴스를 무상태로 유지한다.
- 쿠키 기반 인증이므로 CSRF 토큰을 쿠키로 발급하고, SPA가 헤더로 되돌려 보낸다.
- API 요청이 미인증이면 로그인 페이지로 리다이렉트하지 않고 `401` ProblemDetail을 반환한다. 로그인 이동은 SPA가 결정한다.
- 최초 로그인 시 Keycloak `sub`를 기준으로 로컬 회원을 자동 생성하고, realm 역할을 `ROLE_*` 권한으로 매핑한다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| SPA가 액세스 토큰을 보관 (Bearer) | 브라우저 저장소의 토큰은 XSS로 탈취될 수 있다. 토큰 갱신 로직도 SPA에 필요해진다 |
| 자체 회원 가입·로그인 구현 | 비밀번호 저장과 보안 책임이 생긴다. 학습 목표와 거리가 있다 |
| 인메모리 세션 | 인스턴스를 늘리면 세션이 공유되지 않는다 |

## 결과

- 좋은 점: 브라우저에 토큰이 없다. 인스턴스를 수평으로 늘릴 수 있다.
- 나쁜 점: CSRF 방어가 필요하다. 화면과 API가 동일 오리진이어야 한다 (COM-CON-003).
- 나쁜 점: 브라우저가 실제로 접근할 수 있는 주소로만 로그인이 동작한다. 다른 기기에서 접속하려면 `BBS_HOST`를 설정해야 한다.
