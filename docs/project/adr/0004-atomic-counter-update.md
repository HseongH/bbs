# ADR-0004. 카운터는 원자적 UPDATE로만 바꾼다

- 상태: Accepted
- 일자: 2026-10-08 (최초 결정 2026-09-18, PR #2·#3에서 보강)
- 관련: COM-NFR-010, PST-FR-003, PST-FR-007

## 맥락

조회수와 좋아요 수는 여러 사용자가 동시에 바꾼다. 엔티티를 읽어 `+1` 한 뒤 저장하면, 두 요청이 같은 값을 읽고 각자 저장해서 한 번의 증가를 잃는다 (lost update).

최초 구현은 증감을 원자적 UPDATE로 처리했지만, **게시글 수정과 삭제**가 문제를 다시 만들었다. 두 작업은 도메인 객체 전체를 엔티티로 변환해 저장하는데, 이때 불러올 당시의 카운터 값으로 덮어써서 그 사이에 오른 조회수와 좋아요를 잃었다 (PR #2·#3에서 수정).

## 결정

- 카운터 증감은 `UPDATE post SET like_count = like_count + 1 WHERE id = ?` 형태의 원자적 쿼리로만 한다.
- 감소는 `AND like_count > 0` 조건으로 음수를 막는다.
- JPA 엔티티의 카운터 컬럼은 `updatable = false`로 선언해서, 엔티티 저장이 카운터를 덮어쓰지 못하게 한다.
- 벌크 UPDATE는 `@Modifying(flushAutomatically = true, clearAutomatically = true)`로 선언해서 영속성 컨텍스트와의 불일치를 막는다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 낙관적 락 (`@Version`) | 인기 글에서 충돌과 재시도가 빈번해진다. 카운터처럼 결과가 교환 가능한 연산에 과하다 |
| 비관적 락 (`SELECT ... FOR UPDATE`) | 같은 글의 요청이 모두 직렬화되어 처리량이 떨어진다 |
| Redis에서 집계 후 주기적으로 반영 | 정확도와 장애 처리 설계가 추가로 필요하다. 현재 규모에 과하다 |

## 결과

- 좋은 점: 락 없이 동시 요청에서 정확하다 (`PostLikeConcurrencyTest`, `PostCounterPreservationTest`).
- 나쁜 점: 증감 직후의 값은 같은 트랜잭션의 도메인 객체에 반영되지 않는다. 응답에 담기는 카운터는 증감 전 값일 수 있다.
- 교훈: 원자적 UPDATE만으로는 부족하고, **다른 쓰기 경로가 같은 컬럼을 덮어쓰지 않는지**도 확인해야 한다. 회귀 테스트(`PostCounterPreservationTest`)를 남겼다.
