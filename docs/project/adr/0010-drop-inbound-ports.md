# ADR-0010. 인바운드 포트를 두지 않고 아웃바운드 포트는 애그리게이트마다 하나로 한다

- 상태: Accepted
- 일자: 2026-10-08
- 관련: COM-NFR-030, PR #5, [ADR-0001](0001-hexagonal-architecture-enforced-by-tests.md)(일부 대체), [ADR-0009](0009-feature-boundaries-via-events.md)(일부 대체)

## 맥락

[ADR-0001](0001-hexagonal-architecture-enforced-by-tests.md)에 따라 인바운드 포트(유스케이스 인터페이스) 13개와 아웃바운드 포트 12개를 두었다. 구현을 마친 시점에 돌아보니 다음과 같았다.

- 인바운드 포트 13개는 모두 구현이 하나이고, 컨트롤러 한 곳에서만 주입되었으며, 테스트에서도 목으로 바꾸지 않았다.
- 아웃바운드 포트는 조회·저장·카운터로 잘게 나뉘어 있었지만, 기능마다 어댑터 하나가 모두 구현했다.

인터페이스는 무언가를 대체할 때 가치가 있는데, 이 포트들은 아무것도 대체하지 않으면서 파일 수와 탐색 비용만 늘렸다.

## 결정

- **인바운드 포트를 제거한다.** 컨트롤러, 이벤트 리스너, 다른 기능은 애플리케이션 서비스(`*Service`)를 직접 사용한다. Javadoc은 서비스 메서드로 옮긴다.
- **아웃바운드 포트는 애그리게이트마다 하나로 합친다.** (`PostRepository`, `PostLikeRepository`, `CommentRepository`, `MemberRepository`) 부가 기능 포트(`ViewDeduplicationPort`)는 별도로 유지한다.
- 인바운드 포트가 지켜 주던 경계는 **ArchUnit 규칙으로 옮긴다.** "인바운드 어댑터는 아웃바운드 포트를 참조하지 않는다"를 추가해서, 컨트롤러가 서비스를 우회해 저장소를 직접 호출하지 못하게 한다.
- 기능 경계 규칙의 공개 API를 "도메인과 인바운드 포트"에서 "**도메인과 애플리케이션 서비스**"로 바꾼다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 인바운드 포트 유지 | 대체되는 구현이 없는 인터페이스가 파일 수만 늘린다 |
| 아웃바운드 포트도 제거하고 어댑터를 직접 사용 | `MemberServiceTest`처럼 스프링 없이 인메모리 대역으로 서비스를 테스트하는 효용이 사라진다. 애플리케이션이 JPA 어댑터를 참조하게 되어 계층 규칙과도 충돌한다 |

## 결과

- 좋은 점: 파일 수가 줄고, 컨트롤러에서 구현으로 바로 이동할 수 있다. 서비스 단위 테스트의 효용은 유지된다.
- 나쁜 점: "공개 API"가 인터페이스가 아니라 서비스 클래스의 `public` 메서드가 된다. 서비스의 공개 메서드를 늘릴 때 다른 기능이 쓸 수 있다는 점을 의식해야 한다.
- 발견: 새 규칙을 추가하자 `CurrentMemberArgumentResolver`가 서비스를 우회해 아웃바운드 포트를 직접 쓰고 있던 것이 드러나서, `MemberService`를 거치도록 고쳤다.
- 재검토 조건: 같은 유스케이스에 구현이 둘 이상 필요해지거나(예: 다른 저장 방식), 기능을 별도 모듈·서비스로 떼어 낼 때.
